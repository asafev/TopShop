Module 5 — Mojo IPC System

Mojo is Chromium's inter-process communication framework — the nervous system connecting every process. Understanding Mojo explains how JavaScript API calls actually reach the browser kernel and why automation tools leave detectable traces in the IPC layer.

The Postal System Analogy

Mojo is Chrome's postal system.

Every process has a mailbox. When a renderer wants a cookie, it writes a letter (message) and sends it through a pipe to the browser process's mailbox. The browser reads it, processes the request, and sends a reply back.

There's a strict format for letters (mojom IDL) so both sides know exactly what to expect. Pipes are cheap — you can create millions of them.

💡
Key insight: When you call document.cookie in JavaScript, it doesn't just read memory. It sends a Mojo message to the browser process, waits for a response, and returns the result. This IPC round-trip is measurable and forms the basis of timing-based detection.

Mojo Fundamentals

Mojo replaced Chrome's older "legacy IPC" system (which used IPC::Message with manual serialization). It was introduced around 2015 and is now the only IPC mechanism in Chromium.

Core Primitives

🔗 Message Pipes

Bidirectional channels between two endpoints. Each end can send and receive messages. The fundamental building block.

📊 Data Pipes

Streaming bulk data transfer (like reading a large file). Producer/consumer pattern with backpressure support.

🧠 Shared Buffers

Shared memory regions mapped into multiple processes. Used for large, frequently-accessed data (like compositor frames).

The Interface Pattern: Remote & Receiver

Mojo uses a client-server pattern for structured communication:

  • Remote<T> — The client side. Sends requests, receives callbacks.
  • Receiver<T> — The server side. Receives requests, sends responses.
  • mojom IDL — Interface Definition Language. You define interfaces in .mojom files, and code generation creates C++/JS/Java bindings automatically.

Messages flow Remote → Receiver. The connection is asynchronous — fire-and-forget with optional reply callbacks.

Key Properties

  • Associated interfaces — Multiple interfaces sharing one pipe (preserves message ordering between them)
  • Asynchronous by default — Send and forget, with optional reply callbacks
  • Synchronous calls exist — But are discouraged (block the calling thread, risk deadlocks)
  • Location-transparent — Same API whether the other end is in-process, cross-process, or even cross-machine (theoretically)
  • Ubiquitous — Every IPC in Chrome goes through Mojo: navigation, resource loading, compositor commands, DevTools protocol, permissions queries, etc.

🔬
Detection relevance: Because Mojo is asynchronous and crosses process boundaries, any operation that uses Mojo has inherent latency. Operations that are purely renderer-local (DOM manipulation, math) are orders of magnitude faster. This timing differential is the foundation for IPC-based detection probes.

Mojo Architecture Deep Dive

Layered Architecture

mojom Interface Definition

Interfaces are defined in .mojom files. The build system generates C++, JavaScript, and Java bindings automatically:

// services/network/public/mojom/cookie_manager.mojom
interface CookieManager {
  GetAllCookies() => (array<CanonicalCookie> cookies);
  SetCanonicalCookie(CanonicalCookie cookie) => (bool success);
  DeleteCookies(CookieDeletionFilter filter) => (uint32 num_deleted);
};

Usage in C++ (Browser Process)

// Browser process: bind the remote
mojo::Remote<network::mojom::CookieManager> cookie_manager;
network_context->GetCookieManager(
    cookie_manager.BindNewPipeAndPassReceiver());

// Use it — async by default
cookie_manager->GetAllCookies(
    base::BindOnce([](const std::vector<net::CanonicalCookie>& cookies) {
      // Handle cookies here
    }));

Creating Message Pipes

// Creating a message pipe
mojo::MessagePipe pipe;
// pipe.handle0 and pipe.handle1 are the two endpoints
// Send handle1 to another process, keep handle0 locally

// In practice, BindNewPipeAndPassReceiver() does this for you:
// 1. Creates a new pipe
// 2. Binds one end to the Remote

⚡
Performance: Mojo messages are zero-copy when possible. For shared buffers, no data is copied across processes at all — both sides map the same physical memory pages.

JavaScript Bindings in Blink

Mojo has JavaScript bindings for internal Chrome pages (WebUI). This is how chrome://settings and other privileged pages communicate with the browser process:

// In Blink (renderer), JS can create Mojo interfaces
// This is how internal Chrome pages (WebUI) communicate
// NOT available to normal web pages (security boundary!)
const {CookieManager} = await import('chrome://resources/mojo/...');

// Create a remote to the browser-side CookieManager
const remote = CookieManager.getRemote();
const {cookies} = await remote.getAllCookies();
console.log(cookies);
⚠️
Security boundary: Normal web pages CANNOT use Mojo directly. Only privileged chrome:// pages and extensions can. The renderer sandbox enforces this. But understanding Mojo explains HOW JavaScript APIs work under the hood — every fetch(), document.cookie, and navigator.* access is ultimately a Mojo call.

How the Renderer Bootstraps Mojo

When a new renderer process is spawned, the browser sends it a Mojo invitation:

// content/browser/renderer_host/render_process_host_impl.cc
void RenderProcessHostImpl::Init() {
  // Create the channel mojo invitation
  mojo::OutgoingInvitation invitation;

  // Get the primordial pipe to the child process
  mojo::ScopedMessagePipeHandle pipe =
      invitation.AttachMessagePipe(kChildProcessPipeName);

  // Launch the child process with the invitation
  child_process_launcher_ = std::make_unique<ChildProcessLauncher>(
      ...);

  // The child accepts the invitation and gets access to
  // the pipe, from which all other interfaces are bootstrapped
}

From this single bootstrap pipe, the renderer requests all other interfaces (network, storage, GPU, etc.) via the browser process acting as a broker.

Detection Implications

1. CDP Uses Mojo Internally

When Playwright/Puppeteer connects via CDP (Chrome DevTools Protocol), it opens additional Mojo pipes to the renderer's V8 inspector. This changes the renderer's IPC state — more pipes, more message traffic, more background work.

The inspector Mojo interface (blink::mojom::DevToolsAgent) starts observing console API calls, causing serialization of console arguments that wouldn't normally happen.

2. Runtime.enable Creates Observable Side Effects

When CDP sends Runtime.enable, the V8 inspector begins hooking into console calls. This causes console.log(object) to call toString()/Symbol.toPrimitive on arguments for serialization — a side effect that doesn't happen without DevTools.

// The classic CDP detection:
// When Runtime.enable is active, console serializes args
const trap = new Proxy({}, {
  get(target, prop) {
    if (prop === Symbol.toPrimitive) {
      window.__cdpActive = true; // Only fires under CDP!
    }
    return undefined;
  }
});
console.groupEnd(trap);

3. IPC Timing Side Channel

IPC round-trips add latency. Operations that go through IPC (like document.cookie — needs browser process) have measurably different timing than purely renderer-local operations. CDP adds extra round-trips for instrumentation.

By comparing IPC-bound vs local operation timing, you can detect if extra observers (CDP, DevTools) are adding overhead to the IPC pipeline.

4. Message Ordering Artifacts

Mojo preserves message order on a single pipe but not across pipes. This means certain browser behaviors have deterministic ordering that can be probed. If automation tools introduce additional pipes, ordering guarantees may subtly change.

5. Blink Mojo Bindings Exposure

chrome:// pages expose Mojo to JS. Normal pages can't access Mojo directly, but automated tools sometimes accidentally expose internal bindings or leave traces of the Mojo JS module in the global scope.

6. postMessage and Cross-Process IPC

When postMessage crosses process boundaries (site isolation), it goes through Mojo. This adds latency compared to same-process postMessage. This timing difference can reveal process isolation state — and automated browsers may handle this differently.
