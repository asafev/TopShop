1. What is CDP? — The Remote Control Analogy

CDP is like a universal remote control for your browser.

Imagine your browser is a sophisticated smart TV. You can watch shows (browse pages) using the physical buttons. But there's also an infrared receiver hidden in the back — the DevTools debugging port. Any device that speaks the right protocol (remote control = CDP client) can command the TV: change channels (navigate), take screenshots, read what's on screen, inject content, or monitor everything happening internally.

The TV doesn't know (or care) who is holding the remote — a human developer with DevTools open, a Playwright script, or a Puppeteer bot. It just obeys the protocol messages. This is the fundamental insight for detection: the TV (renderer) can detect that the infrared receiver is active, even if it can't see who's holding the remote.

Key Terms — Deep Dive Definitions

These terms appear everywhere in CDP. Understanding them at the source-code level is essential.

🔧

V8 Inspector

v8/src/inspector/

The debugging interface built directly into V8 (Chrome's JavaScript engine). It's not a separate process or addon — it's compiled into V8 itself. When you open DevTools or Playwright connects, V8 Inspector is the C++ code that responds to Runtime.*, Debugger.*, Profiler.*, and HeapProfiler.* CDP commands.

Analogy: V8 Inspector is like a microphone wired directly into the engine room. It doesn't just observe — it has hooks into the running JavaScript execution to pause it, inspect variables, intercept console calls, and profile memory.

Key classes:

  • V8InspectorImpl — Main coordinator, creates sessions
  • V8RuntimeAgentImpl — Handles Runtime.enable/evaluate/callFunctionOn
  • V8DebuggerAgentImpl — Handles Debugger.enable/setBreakpoint/pause
  • V8Console — Intercepts console.* API calls (this is where Proxy detection lives)

Detection relevance: V8 Inspector runs inside the same isolate as your page's JavaScript. When it serializes console arguments to build CDP events, those property reads happen in the same V8 heap — triggering Proxy traps, getters, and observable side effects.

📂 Browse source: v8/src/inspector/
🎨

Blink Inspector Agents

blink/.../inspector/

The rendering-engine-level CDP handlers inside Blink. While V8 Inspector handles JavaScript execution domains, Blink Inspector handles everything about the rendered page: DOM tree, CSS styles, layout, network requests, page lifecycle.

Analogy: If V8 Inspector is a microphone in the engine room, Blink Inspector is a camera system throughout the building — monitoring the lobby (DOM), the painting gallery (CSS), the mailroom (Network), and the loading docks (Page lifecycle).

Key agents:

  • InspectorDOMAgent — DOM tree, querySelector, getOuterHTML
  • InspectorCSSAgent — Computed styles, stylesheets
  • InspectorPageAgent — Navigation, screenshots, script injection
  • InspectorNetworkAgent — Request/response observation
  • InspectorOverlayAgent — Element highlight overlays

Detection relevance: Blink agents are less directly detectable than V8 Inspector, but Page.addScriptToEvaluateOnNewDocument() and Page.createIsolatedWorld() leave traces. DOM inspection via DOM.getDocument can also trigger MutationObservers.

📂 Browse source: blink/.../inspector/
⚡

Runtime.enable

v8-runtime-agent-impl.cc

The single most important CDP command for detection. When sent, it tells V8 Inspector: "I want to receive executionContextCreated events and consoleAPICalled events."

Analogy: Runtime.enable is like turning on a wiretap on every phone in the building. Once active, every conversation (console call) gets recorded and transmitted to the listener. The phones themselves can detect the wiretap if they're clever enough.

What it activates:

  • Runtime.executionContextCreated — Fired for each execution context (main world, isolated worlds, service workers)
  • Runtime.consoleAPICalled — Fired for every console.* call, with serialized arguments
  • Runtime.exceptionThrown — Unhandled exceptions with stack traces

The detection chain: Runtime.enable → registers console observer → every console.groupEnd(proxyArray) → V8 serializes the proxy to build the event → reads .length property → Proxy trap fires.

Who calls it: Playwright, Puppeteer, DevTools, VS Code debugger — it's one of the first commands sent after connecting.

📖 Official spec: Runtime.enable
🪤

The Proxy Trap

ES2015 Proxy API

A JavaScript Proxy wraps an object and intercepts operations on it (get, set, has, etc.). The "trap" is the handler function that runs when an operation is intercepted. For CDP detection, we use the get trap on an array to detect when V8 Inspector reads .length during serialization.

Analogy: A Proxy trap is like a pressure plate hidden under a doormat. Anyone who steps on it (reads .length) triggers an alarm. Normal visitors (the console spec) know to go around it. But the CDP wiretap (V8 Inspector serialization) doesn't know the pressure plate exists — it walks right over it. 
// The detection mechanism:
const trap = new Proxy([], {
  get(target, prop) {
    if (prop === 'length') {
      // ⚡ This ONLY fires if something reads .length
      // Normal groupEnd: doesn't read it (spec says ignore args)
      // CDP active: reads it (must serialize for consoleAPICalled event)
      detected = true;
    }
    return Reflect.get(target, prop);
  }
});
console.groupEnd(trap); // Spec: ignore args. CDP: serialize → trap fires!

Why it works: V8 Inspector's V8Console class calls createArguments() for every console method when Runtime.enable is active, even for methods like groupEnd() where the spec says arguments should be ignored. This is because the CDP event always includes the args array.

📖 MDN: Proxy   📖 Console spec: groupEnd()
📦

Runtime.RemoteObject

CDP Type

The serialized representation of a JavaScript value sent over CDP. Every time V8 needs to tell a CDP client about a JS object, it converts it into a RemoteObject — and this conversion is where property reads happen.

Structure:

{
  "type": "object",       // object|function|undefined|string|number|boolean|symbol|bigint
  "subtype": "array",     // array|null|node|regexp|date|map|set|weakmap|proxy|...
  "className": "Array",   // constructor name
  "description": "Array(0)", // ← reads .length to build this!
  "objectId": "1234"      // handle for further inspection
}

The description field for arrays is built as "Array(N)" where N = .length. This is why the Proxy .length trap fires — V8 must read it to build the RemoteObject description.

📖 Official spec: RemoteObject
📡

Runtime.consoleAPICalled

CDP Event

The CDP event fired every time page JS calls a console method. This is the event that causes argument serialization. Without this event (i.e., Runtime.enable not sent), V8 has no reason to serialize console arguments to RemoteObjects.

Full event structure:

{
  "method": "Runtime.consoleAPICalled",
  "params": {
    "type": "endGroup",           // console method name
    "args": [{                    // ← SERIALIZED arguments
      "type": "object",           //   Each arg = RemoteObject
      "subtype": "array",         //   Serialization reads properties
      "description": "Array(0)"   //   ← .length was read HERE
    }],
    "executionContextId": 1,      // Which world
    "timestamp": 1715788800.123,  // When it happened
    "stackTrace": {               // Where in code
      "callFrames": [...]
    }
  }
}

Event types (the type field): log debug info error warning dir dirxml table trace clear startGroup startGroupCollapsed endGroup assert count timeEnd

The endGroup type corresponds to console.groupEnd() — the key detection vector because the spec says to ignore args, but CDP serializes them anyway.

📖 Official spec: consoleAPICalled

2. CDP Architecture — How the Protocol Flows Through Chrome

CDP isn't a single monolithic system. It's a distributed protocol with handlers split across three layers:

Transport Layer — WebSocket + JSON-RPC

Chrome opens an HTTP server on --remote-debugging-port=PORT. Clients discover targets via /json/list then upgrade to a WebSocket connection. All messages are JSON-RPC: {id, method, params} for commands, {id, result} for responses, {method, params} for events.

// Discover targets
GET http://localhost:9222/json/list
→ [{ "id": "ABC123", "webSocketDebuggerUrl": "ws://localhost:9222/devtools/page/ABC123" }]

// Connect via WebSocket
ws = new WebSocket("ws://localhost:9222/devtools/page/ABC123")

Browser-Side Routing — DevToolsManager

The browser process receives WebSocket frames and routes them. "Browser-level" domains (Browser, Target, SystemInfo) are handled here. "Page-level" domains are forwarded to the correct renderer via Mojo IPC.

// Chromium source path:
// content/browser/devtools/devtools_http_handler.cc    — HTTP + WS server
// content/browser/devtools/devtools_manager.cc         — Session management
// content/browser/devtools/devtools_agent_host_impl.cc — Per-target routing
// content/browser/devtools/protocol/*                  — Browser-side handlers

Renderer-Side Handlers — V8 Inspector + Blink Agents

This is where detection happens. The renderer process has two types of CDP handlers:

  • V8 Inspector (v8/src/inspector/) — Handles Runtime, Debugger, Profiler, HeapProfiler domains. Runs inside V8 itself.
  • Blink Inspector Agents (third_party/blink/renderer/core/inspector/) — Handles DOM, CSS, Page, Network, Overlay, and other Blink-specific domains.
// Key V8 Inspector files:
// v8/src/inspector/v8-inspector-impl.cc       — Main inspector
// v8/src/inspector/v8-runtime-agent-impl.cc   — Runtime domain
// v8/src/inspector/v8-console.cc              — Console API interception
// v8/src/inspector/v8-debugger.cc             — Debugger domain

// Key Blink Inspector files:
// blink/renderer/core/inspector/inspector_dom_agent.cc
// blink/renderer/core/inspector/dev_tools_host.cc
// blink/renderer/core/inspector/main_thread_debugger.cc

The Mojo Bridge — DevToolsAgent Interface

Browser and renderer communicate CDP messages over the blink.mojom.DevToolsAgent Mojo interface. This is a critical bridge: the browser process sends serialized CDP commands, the renderer processes them and sends back results + events.

// Mojo interface definition:
// third_party/blink/public/mojom/devtools/devtools_agent.mojom
//
// interface DevToolsAgent {
//   AttachDevToolsSession(...)  → creates session
// }
//
// interface DevToolsSession {
//   DispatchProtocolCommand(int call_id, string method, bytes message)
// }
//
// interface DevToolsSessionHost {
//   DispatchProtocolNotification(string method, bytes message)  ← events
// }
💡
Why this matters for detection: Steps 1-2 (transport and routing) happen outside the renderer and are invisible to page JavaScript. But Step 3 (V8 Inspector) runs inside the same process as your page code. This shared execution context is what creates detectable side effects.

3. CDP Domains Explorer — The API Surface

CDP organizes functionality into domains. Each domain has Methods (commands you send), Events (notifications you receive), and Types. There are ~50 domains. Here are the ones most relevant to detection:

Runtime CRITICAL

JS execution, console interception, object inspection. Runtime.enable activates console observation — the root cause of most detection signals.

Debugger CRITICAL

Breakpoints, stepping, pause/resume. Debugger.enable changes how debugger statements behave — creates timing detection vector.

Page DETECTION

Navigation, screenshots, script injection. Page.addScriptToEvaluateOnNewDocument injects code that may leave traces.

Network DETECTION

Request interception, caching behavior. Enabled network observation adds overhead detectable via timing.

DOM

DOM tree inspection, node resolution. Requires walking DOM tree which can create observable mutation records.

Emulation

Device metrics, geolocation, timezone overrides. Creates JS-visible inconsistencies (timezone ≠ locale).

Target

Target discovery, session management, auto-attach. Browser-level domain, not directly observable from page JS.

Input

Synthetic keyboard/mouse/touch events. Creates "untrusted" events detectable via event.isTrusted.

4. Runtime Domain Deep Dive — Where Detection Lives

The Runtime domain is the #1 source of detectable side effects. Let's trace exactly what happens when Runtime.enable is sent:

Client sends Runtime.enable

This is one of the first commands Playwright/Puppeteer sends after connecting. It tells V8: "I want to know about execution contexts and console API calls."

V8 Inspector registers console observer

Inside V8, the Runtime agent registers itself as a console delegate. Now every console.log(), console.warn(), console.groupEnd() etc. triggers a callback in the inspector.

// v8/src/inspector/v8-runtime-agent-impl.cc
void V8RuntimeAgentImpl::enable() {
  m_enabled = true;
  // ... registers console message handler
  // Now ALL console API calls get intercepted
}

Console call → argument serialization

When page JS calls console.log(someObject), V8 must serialize someObject into a Runtime.RemoteObject to send via CDP. This serialization reads properties — triggering getters, Proxy traps, and toString() calls.

// v8/src/inspector/v8-console.cc — Console API interception
void V8Console::Log(const v8::FunctionCallbackInfo<v8::Value>& info) {
  // ... builds consoleAPICalled event
  // Must serialize each argument:
  //   → reads .length on array-like objects
  //   → calls .toString() on objects  
  //   → triggers Proxy get/has traps
  //   → invokes getters on accessor properties
}

Event dispatched to client

The serialized console call becomes a Runtime.consoleAPICalled event sent back through Mojo → WebSocket → client.

// The CDP event:
{
  "method": "Runtime.consoleAPICalled",
  "params": {
    "type": "log",
    "args": [{ "type": "object", "description": "Array(0)" }],
    "executionContextId": 1,
    "timestamp": 1234567890.123
  }
}
🔍
The detection opportunity: Between Steps 3 and 4, V8 accessed properties on the console argument that it normally wouldn't access. If that argument is a Proxy, the trap fires. If it has a getter, the getter runs. This is not a bug — it's a fundamental architectural consequence of how CDP serialization works.

6. Detection Vectors — Observable Side Effects

These are the CDP side effects that inline page JavaScript can observe. Ranked by reliability:

🎯 Proxy Trap on console.groupEnd()

Reliability: Very High. The spec says groupEnd() ignores args. CDP serializes them anyway. Pass a Proxy array — if .length is read, CDP is active.

Detects: Any CDP client with Runtime.enable (Playwright, Puppeteer, DevTools open).

False positives: DevTools open (same mechanism). Distinguish with additional signals.

🕵️ Error.stack Frame Injection

Reliability: High. Code injected via Runtime.evaluate() or Page.addScriptToEvaluateOnNewDocument() leaves stack trace signatures containing __playwright_evaluation_script__, pptr://, or anonymous (eval) frames.

⏱️ Console Method Timing Delta

Reliability: Medium. With CDP, console methods take longer because V8 must serialize arguments and dispatch events. Measurable with performance.now().

⏸️ debugger Statement Latency

Reliability: Medium. With Debugger.enable, the debugger; statement creates a pause event that Playwright must immediately resume. This takes measurably longer than in a normal browser.

🌐 Execution World Leaks

Reliability: Medium. Playwright creates isolated worlds for page.evaluate(). Functions or bindings added via Runtime.addBinding() or Page.createIsolatedWorld() can leak observable globals.

📊 Performance Observer Anomalies

Reliability: Low-Medium. CDP operations (screenshots, DOM queries) cause performance entries and layout recalculations that can be observed via PerformanceObserver.

🧪 Lab 1: The Proxy Trap — console.groupEnd() Serialization

How it works — Visual Step-by-Step

Create a Proxy array — We wrap an empty array with a Proxy that intercepts get operations. Specifically, we watch for reads of the "length" property.
Pass it to console.groupEnd() — Per the console spec (console.spec.whatwg.org), groupEnd() should just "pop the group stack" and ignore any arguments.
Without CDP: V8 follows the spec → ignores the argument → Proxy trap never fires → .length access count = 0.
With CDP (Runtime.enable): V8 Inspector must serialize the argument into a RemoteObject for the consoleAPICalled event → reads .length to determine it's an array of size 0 → Proxy trap fires! → count ≥ 1.

🧪 Lab 2: Error.stack Injection Fingerprint

How it works

When Playwright or Puppeteer inject JavaScript via Runtime.evaluate(), Runtime.callFunctionOn(), or Page.addScriptToEvaluateOnNewDocument(), the injected code runs in a special context. The Error().stack reveals this:

  • Playwright: Stack contains __playwright_evaluation_script__
  • Puppeteer: Stack contains pptr:// protocol
  • Runtime.evaluate: Stack shows eval at <anonymous> or unusual URLs
  • Normal inline script: Stack shows the actual page URL and line numbers

Note: Inline page scripts (in <script> tags) won't show injection signatures because they're loaded normally. But any code injected after the fact via CDP will have a different stack origin.

🧪 Lab 3: Console Method Timing Oracle

How it works

With CDP Runtime.enable active, every console call has additional overhead because V8 must:

  1. Serialize all arguments into RemoteObject format
  2. Build the consoleAPICalled event JSON
  3. Dispatch the event through the protocol pipeline to the CDP client

This overhead is measurable. We compare the time to call console.log() with a complex object vs. a simple primitive. With CDP active, complex objects take significantly longer because serialization must traverse their properties.

🧪 Lab 4: debugger Statement Timing

How it works

The debugger; JavaScript statement behaves differently depending on whether Debugger.enable has been sent via CDP:

  • No debugger attached: The statement is a no-op. Takes < 0.01ms.
  • Debugger.enable active: V8 fires a Debugger.paused event. The CDP client (Playwright) must send Debugger.resume to continue. This round-trip takes measurably longer (0.5-5ms+ depending on network).
  • DevTools open: Execution pauses until the developer clicks "Resume". Indefinite time.

Stealth note: Playwright uses Debugger.setInstrumentationBreakpoint and carefully handles debugger statements, but the timing signature is still present.

🧪 Lab 5: Execution World Detection

How it works

CDP supports multiple execution contexts (worlds) within a single page. Playwright creates isolated worlds via Page.createIsolatedWorld() for its utility scripts, and uses Runtime.addBinding() to expose Node.js callbacks to page JavaScript.

These operations leave traces:

  • Runtime.addBinding("name") adds a function to the global scope that pages can discover
  • Playwright adds bindings like __playwright_binding__ or exposes utilities
  • The executionContextCreated event reveals world names like "__playwright_utility_world__"
  • Pages can enumerate globals to find unexpected bindings

🧪 Lab 6: Runtime.addBinding Leak Detection

How it works

Runtime.addBinding(name) is a CDP method that creates a JavaScript function in the page's global scope. When page code calls this function, a Runtime.bindingCalled event fires on the CDP client. Playwright uses this mechanism to create a communication channel between the page and Node.js.

The leak: These binding functions have unique characteristics:

  • They are native functions (created by V8, not compiled JS)
  • Function.prototype.toString() returns "function name() { [native code] }"
  • They accept exactly one string argument — calling with anything else throws
  • They appear in the global scope but weren't in the original page's <script> tags

9. CDP via Chrome Extensions — chrome.debugger API

Chrome extensions can use CDP through the chrome.debugger API. This is relevant because:

🔬 Protocol Monitor — How to Read CDP Traffic

Chrome's Protocol Monitor tab (available via DevTools → ⋮ → More tools → Protocol monitor) records every CDP message flowing between the browser and any connected client. When an AI agent like OpenClaw fills a form, this tab captures the exact commands it sends. The problem? There is a LOT of noise. A 685-entry capture might contain only ~36 entries that are the actual form-filling commands — the rest is background telemetry, style updates, and script parsing.

Understanding the Protocol Monitor Columns

Each row in the Protocol Monitor has these key columns:

📋 Protocol Monitor Column Reference
ColumnWhat It ShowsWhy It Matters
↕ Type (arrow icon) Direction: ↓ = sent TO browser (command), ↑ = received FROM browser (event/response) Commands with an id field are requests you can correlate with responses. Events (no id) are push notifications.
📌 Method The CDP domain + method name, e.g. Runtime.evaluate, DOM.requestNode This is the most important column — tells you WHAT action was taken. The domain prefix tells you which subsystem.
📤 Request The JSON parameters sent with the command (truncated in the table, click to expand) For Runtime.evaluate, shows the expression field — the actual JS code being injected.
📥 Response The JSON result returned by Chrome For evaluate commands, shows the return value — tells you what DOM element was found.
🏷️ ID Sequential message ID (only for request/response pairs) Events (like Debugger.scriptParsed) have no id — they are unsolicited notifications.
⏱️ Elapsed Time Round-trip time in milliseconds Form-fill commands typically complete in 0-2ms. Slower commands may indicate network activity or complex DOM operations.
🎯 Target / Session Which browser target (tab) and CDP session this message belongs to Useful when multiple tabs are open. All form-fill commands share the same sessionId.

The Key CDP Methods You'll See

When an AI agent fills a form, these are the CDP methods that appear — organized by role:

⚡

Runtime.evaluate

Runtime Domain

THE core command. Executes JavaScript in the page context. The agent uses this to locate form elements.

In OpenClaw's case: window.getNodeForIndex(11) — calls a pre-injected helper to get an element by its accessibility tree index.

The response contains the element description: HTMLInputElement with the full CSS selector, plus an objectId that's a handle to the live JS object.

Analogy: Like pointing at a form field and saying "that one!" — the browser returns a ticket number (objectId) you can use to reference it.
🌳

DOM.requestNode

DOM Domain

Converts a JavaScript object reference (objectId) into a DOM node ID (nodeId) in Chrome's internal DOM tree.

This is needed because the Runtime domain and DOM domain use different ID systems. The nodeId is required for DOM operations like focusing, clicking, or reading attributes.

Analogy: Converting a person's name (objectId) into their employee badge number (nodeId) so the security system can recognize them.
🗑️

Runtime.releaseObject

Runtime Domain

Releases a JavaScript object handle so V8's garbage collector can reclaim it. Sent after DOM.requestNode because the objectId is no longer needed.

Every Runtime.evaluate that returns an object creates a handle — if not released, it leaks memory. The agent is being "clean" by releasing after use.

Analogy: Returning a library book after you've copied the page number you needed.
📜

Debugger.scriptParsed

Debugger Domain

EVENT (not a command). Chrome fires this whenever any JavaScript is parsed — including every Runtime.evaluate call. This is the #1 source of noise in the Protocol Monitor.

The url field is key: scripts injected by the agent show pptr:evaluate;functionName — a dead giveaway of Puppeteer/CDP automation.

Detection insight: The pptr: URL prefix is a fingerprint! Normal page scripts have https:// URLs.
📡

Runtime.bindingCalled

Runtime Domain

EVENT — NOISE. Fired when a page calls a function registered via Runtime.addBinding. In Protocol Monitor captures, this is mostly DevTools' own performance metrics reporter: __chromium_devtools_metrics_reporter.

These appear in huge bursts (144 out of 685 entries!) and contain INP/interaction timing data. Completely irrelevant to understanding what the agent did.

Tip: Filter these out first — they're DevTools talking to itself, not the agent talking to the browser.
🎨

CSS / Animation / Audits

Various Domains

EVENTS — NOISE. Background activity from the page itself:

  • CSS.styleSheetChanged — page CSS animations/transitions updating
  • Animation.animationCreated/Started/Canceled — CSS animations lifecycle
  • Audits.issueAdded — DevTools audit warnings (performance, cookies)
  • DOM.setChildNodes — Chrome pushing DOM subtree data it thinks you might need
Tip: These are the page "breathing" — completely normal background activity, not agent commands.

Key Insight: The 3-Command Pattern

Every form field interaction follows a repeating cycle of exactly 3 CDP commands:

  1. Runtime.evaluate → "find element N" → returns objectId
  2. DOM.requestNode → "convert objectId to nodeId" → returns nodeId
  3. Runtime.releaseObject → "release objectId handle" → cleanup

This cycle repeats 12 times per field for short text inputs (like "koko" = 4 chars). Why 12 and not 4? Because the agent polls the element on each keystroke AND between keystrokes to verify it's still connected. This polling pattern is a detection fingerprint — real humans don't re-query the DOM between every keystroke.

Puppeteer vs Playwright: Both speak CDP, but Playwright also has its own protocol. The pptr: prefix is Puppeteer-specific — Playwright would show playwright: or different patterns. This is a clear forensic fingerprint.

❓ Where Are the Typed Values? Why Can't You See "asaf" or "koko"?

This is the most important thing to understand about Protocol Monitor.

The values "asaf", "koko", "jumbo", etc. are typed using Input.dispatchKeyEvent CDP commands — one per keystroke. For "koko" that's 4 separate Input.dispatchKeyEvent calls with {type: "keyDown", key: "k"}, {key: "o"}, {key: "k"}, {key: "o"}.

But these are NOT in your capture. Here's why:

  1. Protocol Monitor only captures what's in its active session. Your capture's command IDs start at 658 — meaning IDs 1-657 happened before you opened Protocol Monitor or before the recording window. The Input.dispatchKeyEvent commands were sent but are in that missing range, or they went through Puppeteer's internal CDP session which Protocol Monitor doesn't always intercept.
  2. Puppeteer uses Input.dispatchKeyEvent through its own CDP session. The fillFormElement script (running in ctx=10) calls Puppeteer's keyboard.type("koko") internally. Puppeteer sends Input.dispatchKeyEvent directly over the CDP pipe — these are "fire-and-forget" commands that may not be captured by Protocol Monitor's event listener if it wasn't subscribed to the Input domain.
  3. The only place you CAN see the values is in Network requests triggered as side-effects (like the ZoomInfo email validation: {"email":"asaf@outlook.com"}) or by adding Input domain monitoring before the agent starts.
💡 How to Capture the Keystrokes Next Time

To see Input.dispatchKeyEvent in Protocol Monitor:

  1. Open Protocol Monitor before asking the agent to fill anything
  2. Make sure the filter field is empty (don't filter to specific domains)
  3. Look for entries with method Input.dispatchKeyEvent and Input.dispatchMouseEvent
  4. The params.key field will show each individual keystroke
  5. The params.text field shows the character being inserted

Alternatively, you can intercept keystrokes from the page side by adding document.addEventListener('keydown', e => console.log(e.key)) before the agent starts. These will show up in the Console as each character is "typed" by Input.dispatchKeyEvent.
