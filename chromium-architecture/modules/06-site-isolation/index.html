Module 6 — Site Isolation

Site Isolation is Chromium's strongest security boundary — one process per site. It defends against Spectre, compromised renderers, and cross-site data theft. Understanding it reveals how process assignment works and where detection probes can observe process boundaries.

The Apartment Building Analogy

Imagine an apartment building where each apartment has its own door lock (Same Origin Policy).

Before Site Isolation, all apartments shared the same hallway and a thief who picked one lock could peek into others. The locks (SOP) only worked if everyone played fair — a compromised renderer (thief with tools) could bypass them entirely.

Site Isolation gives each apartment its own separate building with its own guard. Even if a thief breaks into one building, they can't reach others. There's no shared hallway to exploit.

This is what Chrome 67 introduced: one process per site.

🧪
Try it now: Open chrome://process-internals/#web-contents in Chrome. Navigate to a page with cross-site iframes (any page with third-party ads). You'll see each site in its own process with its own ProcessLock.

Site Isolation Fundamentals

The Problem

Before Site Isolation, cross-site iframes shared the renderer process with the parent page. A compromised renderer could access data from other sites in the same process.

Spectre attacks (2018) made this urgent: Spectre can read ANY data in the same process via CPU speculative execution side channels. If cross-site data lives in the same process, it's already compromised — no exploit needed beyond JavaScript.

The Solution

Give each site (scheme + eTLD+1, e.g., https://example.com) its own renderer process. No cross-site data ever coexists in the same address space.

Site vs Origin

Site (scheme + eTLD+1)

  • https://a.example.com
  • https://b.example.com
  • https://example.com:8080

All same site — share a process. Ignores subdomains, port, path.

Origin (scheme + host + port)

  • https://a.example.com
  • https://b.example.com ← different origin!
  • https://example.com:8080 ← different origin!

All different origins. More granular but breaks document.domain compat.

Key Concepts

SiteInstance

The core abstraction — a group of documents from the same site in the same browsing context group. All documents in a SiteInstance share a process.

Out-of-Process iFrames (OOPIF)

Cross-site iframes run in a different renderer process from their parent. Composited visually into the right location by the GPU process.

ProcessLock

Each renderer process is "locked" to a specific site. The browser process enforces this: the locked renderer can only access data for its site.

CORB / ORB

Cross-Origin Read Blocking: the browser process blocks sensitive cross-site data (HTML, XML, JSON) from being delivered to a renderer that shouldn't have it.

Site Isolation Architecture

Process Assignment with OOPIFs

Key Abstraction Relationships

BrowsingInstance (browsing context group)
  └── SiteInstance (one per site per BrowsingInstance)
        └── RenderProcessHost (one per SiteInstance, may be shared)
              └── RenderFrameHost (one per document)

A BrowsingInstance groups all tabs/frames that can script each other (same browsing context group). Each SiteInstance within it represents one site and maps to exactly one process. A RenderFrameHost represents a single document within that process.

Navigation Flow with Site Isolation

  1. User clicks link from site-a.com to site-b.com
  2. Browser creates NavigationRequest
  3. Browser checks: site-b.com needs different process (different site)
  4. Browser creates or reuses process locked to site-b.com
  5. Old renderer process unloads document, new process loads it
  6. Browser commits navigation to new renderer → cross-process navigation complete

This is called a "process swap" — the browser replaces the RenderFrameHost for the frame with one in the correct process. The old one may be cached in the Back-Forward Cache.

OOPIF Visual Compositing

When a cross-site iframe renders in a different process, it doesn't have access to the parent's compositor surface. Instead:

  1. The OOPIF renderer composites its frame content into a Surface
  2. The Surface ID is sent to the parent renderer via the browser process
  3. The parent renderer embeds the Surface ID at the correct position in its own compositor tree
  4. The Viz/GPU process composites both surfaces together for final display

This is why OOPIF rendering has slightly different paint timing characteristics — observable via PerformanceObserver.

⚡
Performance cost: Site Isolation uses ~10-13% more memory on desktop due to additional renderer processes. Each process has its own V8 heap, Blink instance, and compositor. Google considered this acceptable given the security benefit against Spectre.

ProcessLock Enforcement

The browser process enforces that a locked renderer can only access data for its assigned site:

// content/browser/child_process_security_policy_impl.cc
bool ChildProcessSecurityPolicyImpl::CanAccessDataForOrigin(
    int child_id, const url::Origin& origin) {
  auto* process_lock = GetProcessLock(child_id);
  if (!process_lock || process_lock->is_invalid())
    return true;  // unlocked process — can access anything

  // Check if this origin matches the process's lock
  SiteInfo site_info = SiteInfo::CreateOnIOThread(origin);
  return process_lock->IsCompatibleWithSiteInfo(site_info);
  // If false → browser blocks the request!
  // This prevents compromised renderers from stealing cross-site data
}

This is the critical check — even if a renderer is fully compromised (arbitrary code execution), it cannot request data for a different site. The browser process will refuse.

⚠️
Important: Site Isolation is enforced by the browser process, not the renderer. A compromised renderer cannot bypass it because the ProcessLock check happens in a separate, privileged process. This is the fundamental security property — the browser process is the trusted computing base.

Detection Implications

1. OOPIF Timing Side Channel

Cross-site iframes in different processes have measurably different postMessage latency compared to same-site iframes (same process). Same-process messages are near-instant (shared memory queue), while cross-process messages require Mojo IPC round-trips through the browser process.

This timing difference can reveal process isolation state and detect if site isolation is enabled or disabled (e.g., in WebView or Electron).

2. SharedArrayBuffer Availability

SharedArrayBuffer is only available in CrossOriginIsolated contexts (pages served with COOP + COEP headers). Its presence or absence reveals the page's isolation configuration.

Automated environments may serve different headers, revealing their nature.

3. performance.measureUserAgentSpecificMemory()

Returns memory breakdown per origin — only available with cross-origin isolation. Can reveal process structure and the number of separate origins loaded in the page's agent cluster.

4. Cross-Origin Opener Policy (COOP)

Affects window.opener behavior and process isolation. COOP: same-origin severs the opener relationship for cross-origin popups, which affects detection probes that rely on opener references.

5. Electron / VS Code Differences

VS Code's Electron may not enforce full site isolation. SiteInstance grouping may differ. webPreferences.contextIsolation and nodeIntegration settings affect how cross-origin resources behave — creating detectable differences from standard Chrome.

6. document.domain Behavior

document.domain assignment reveals whether origin-keyed agent clusters are enforced. In origin-keyed mode (new default), setting document.domain has no effect and cross-subdomain scripting is blocked — a behavioral difference that can be probed.

7. Frame Timing Attacks

OOPIF vs same-process iframe have different layout/paint timing characteristics. Cross-process frames must go through Surface composition, adding latency observable via PerformanceObserver with entryTypes: ['paint', 'layout-shift'].
