Module 1 — Multi-Process Architecture Overview

Why does Chromium use multiple OS processes? What are they? How do they relate to each other? This module is the foundation for everything that follows.

The Operating System Analogy

Think of Chrome as a mini operating system.

In the early days, browsers were like single-tasked DOS: one misbehaving page could crash everything. Chrome's design mirrors a modern OS where each application (web page) runs in its own isolated process.

🧪
Try it now: Open Chrome Task Manager (Shift+Esc). You'll see separate entries for "Browser", each tab, GPU Process, and more. Each has its own PID (Process ID).

Why Multiple Processes?

Around 2006, browsers were monolithic single-process applications. A bug in the rendering engine or a misbehaving plugin could crash the entire browser. Chromium's multi-process architecture was designed to solve three problems:

🛡️ Stability

A crash in one renderer (tab) doesn't bring down the rest. The browser shows a "sad tab" and other tabs keep working.

🔒 Security

Each renderer runs in a restricted sandbox. Even if an attacker compromises a renderer, they can't access files, network, or other sites directly.

⚡ Performance

Separate processes run in parallel on multi-core CPUs. One tab doing heavy JS doesn't freeze others. The OS can manage memory per-process.

The Four Main Process Types

ProcessRoleSandboxed?Count
Browser Process UI, network, storage, child process management, security policy enforcement No (privileged) Exactly 1
Renderer Process Runs Blink (HTML/CSS layout) + V8 (JavaScript). Paints web content. Yes (most restricted) 1 per site (with site isolation)
GPU Process Executes GL/Vulkan/D3D commands on behalf of renderers. Composites final frame. Partial (Low integrity) Exactly 1
Utility Process Sandboxed helper tasks: codecs, data decoding, network service, storage service Yes Several
🔬
Detection relevance: Understanding process boundaries is key. JavaScript in a renderer cannot directly call OS APIs — it must ask the browser process via IPC. This boundary creates observable artifacts: latencies, restricted APIs, and behaviors that differ between a real Chrome and an automated one (Playwright/Electron).

The Communication Backbone

Processes communicate via Mojo IPC — Chromium's inter-process communication system. It replaced an older "legacy IPC" system. Every cross-process action (navigation, setting a cookie, painting to screen) goes through Mojo message pipes.

Architectural Deep Dive

Process Lifecycle

When Chrome starts, the browser process launches first. It creates the UI, initializes services, and then spawns renderer processes on demand as you open tabs.

Key Architectural Relationships

Browser-side class↔Renderer-side classPurpose
RenderProcessHost↔RenderProcessManages one browser↔renderer IPC connection
RenderFrameHost↔RenderFrameManages a single document/frame (the workhorse)
RenderViewHost↔RenderViewLegacy: represents a tab's view (being phased out)
RenderWidgetHost↔RenderWidgetInput events + painting for a widget
📐
Design pattern: For every object in the renderer there's a "Host" counterpart in the browser process. The browser side is privileged and makes security decisions; the renderer side is sandboxed and does the actual work. Communication between them goes through Mojo.

Process Sharing & Limits

Chrome doesn't create unlimited processes. A soft process limit (based on available RAM) determines when Chrome starts reusing existing processes for same-site content. On desktop, iframes from site A in a page from site B get their own process (Out-of-Process iFrames — OOPIFs).

Detection Angle: What JS Can Observe

🎯
The multi-process architecture creates observable boundaries that JavaScript can probe. Here's why this matters for detection.

Process Boundaries Create Detectable Artifacts

1. Sandboxed APIs Behave Differently

The renderer can't access the network directly — it asks the browser process. This means fetch() calls go through IPC. In automated browsers like Electron (which Copilot uses), the IPC path differs because the browser process is VS Code, not Chrome.

// In real Chrome: navigator.plugins has PDF viewer, etc.
console.log(navigator.plugins.length);  // Chrome: 5, Electron: 0

// The plugins list is populated by the browser process via IPC
// Electron's browser process doesn't register Chrome's plugins

2. Process Count & Memory

performance.memory (Chrome-only, deprecated) reflects the renderer's JS heap — a single process view. The values differ between a normal renderer and an Electron renderer.

// Chrome-specific: JS heap info for THIS renderer process
if (performance.memory) {
  console.log({
    jsHeapSizeLimit: performance.memory.jsHeapSizeLimit,
    totalJSHeapSize: performance.memory.totalJSHeapSize,
    usedJSHeapSize: performance.memory.usedJSHeapSize
  });
  // Electron/Copilot may have different heap limits
}

3. Cross-Origin Isolation

Site Isolation means cross-origin iframes run in different processes. This creates timing differences when communicating with iframes (postMessage crosses process boundaries). Playwright's page.evaluate runs in the renderer but is injected via CDP (Chrome DevTools Protocol), which uses Mojo IPC — creating detectable side effects.

4. The CDP Connection (Chrome DevTools Protocol)

When DevTools or Playwright connect to Chrome, they use CDP which enables Runtime.enable in the renderer's V8 inspector. This causes V8 to serialize console arguments — triggering Proxy traps that wouldn't fire otherwise. This is the #1 detection vector for CDP-controlled browsers.

// CDP detection: when Runtime.enable is active, console calls
// serialize their arguments, triggering Proxy traps
const detector = new Proxy({}, {
  get: function(target, prop) {
    if (prop === Symbol.toPrimitive) {
      // This fires when CDP serializes console output
      // but NOT in a normal browser without DevTools
      window.__cdpDetected = true;
    }
    return undefined;
  }
});
console.groupEnd(detector);
